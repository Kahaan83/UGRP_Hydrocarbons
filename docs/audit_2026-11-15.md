## 0. Bottom line

1. **"Certified for sure" cannot come from this repo alone.** In this project "certified" means: every spec constraint passes under the
   model *and* a declared, validated one-sided margin, on verified spec limits and verified pure constants. That is a model-level statement.
   A fuel is certified in fact only by laboratory testing (ASTM D1655 / D7566 / IS 1571 test methods; a new synthetic pathway also needs
   ASTM D4054 qualification). The roadmap already names the true final check: `results/v5/BASE/delta_ws7_design_realism/LAB_TEST_REQUEST.md`
   (waiting on your decision; nobody has been contacted).
2. **Current model-level status: 0 designs are certified under the current (verified) spec set.**
   * Since the D86 limits were verified (CLM-66), D7566 T50-T10 / T90-T10 apply to every synthetic blend: **0 of 8 certified**.
   * The two pool C designs that CLM-63 called certified were certified with **D86 off**. With D86 on, the same recipe family (P0) fails
     T90-T10 (49.9 C, against 40 C plus the 18.25 C margin) as well as flash, freezing and smoke. `LAB_TEST_REQUEST.md` already says so.
     CLM-63 now carries a "superseded for the full spec by CLM-66" note (added in this audit), so it is not read as a live claim.
3. **New finding (section 3): the "0.0008 slack" misses of P2/P3 are not tolerance noise.** The 25 mm primary smoke limit and the 8 vol %
   aromatics minimum cannot both be met under the bulk smoke regression, which predicts 24.97 mm at 8 vol %. The max-min optimiser spreads
   that conflict equally over smoke, aromatics and density or freezing. The judge scores smoke on the alternative branch, but the optimiser
   only sees the primary branch, because the naphthalenes requirement of a represented blendstock has no margin. These designs would still
   be uncertified for other reasons (section 4), but they would no longer *fail* a limit.
4. **Code works.** The prediction API runs on the physics route with no fallback (the fallback bug recorded in memory on 2026-11-12 is fixed).
   Test suite: see section 1.
5. **Cleanup.** The repo has little stale *tracked* content: almost every legacy path is still referenced by code or cited as evidence.
   About 230 MB of untracked scratch can go (section 6). That needs your one-time OK, because untracked files cannot be recovered.

## 3. Root cause of the P2/P3 "-0.0008 slack" failures (diagnostic, not a declared reading)

Observation: four different designs (P2 and P3, ASTM and BIS) report **exactly** `min_slack = -0.000820` on *different* constraints
(density and aromatics for ASTM; freezing and aromatics for BIS).

Diagnostic (scratch script; the recorded recipe rescored with `engine_v4._Sides.vector`, with each entry labelled by its constraint and bound,
then re-optimised with lambda = 0):

* The optimiser's three lowest slacks, labelled:
  * ASTM: `aromatics_vol_pct_min` -0.000885, `density_15C_kg_m3_min` -0.000851, `smoke_point_mm_min` -0.000806.
  * BIS: `aromatics_vol_pct_min` -0.000938, `freezing_point_C_max` -0.000822, `smoke_point_mm_min` -0.000794.
  * The next slacks agree with the judge: FBP 0.0155, NHOC 0.0247, freezing 0.106.
  * `sides.alt["smoke_point_mm"]` is **None** in both specs: the alternative branch is dead in the optimiser.
  * Smoke 24.979 mm against 25 mm gives (25 - 24.979) / 25 = 0.00082.
* With lambda = 0 the ASTM recipe changes (Jet A 0.549, HEFA 0.209, ATJ 0.243). Density then passes at the point estimate (775.75), but
  aromatics is again **7.9861 vol %** and smoke again **24.979 mm**. The BIS recipe is unchanged.
* `smoke_point_from_bulk` gives 24.97 mm at 8.0 vol % aromatics (roadmap, WS1 arithmetic). So the 25 mm primary limit and the 8 vol % minimum
  are mutually exclusive under this model. The max-min optimum splits the miss equally, at -0.00082 on each binding constraint.
* The judge reports smoke on the alternative branch (slack +0.31 to +0.39, `uncertified`). The optimiser cannot use that branch:
  `engine_v4._Sides._build_alt` returns `None` (branch dead) when a requirement, here naphthalenes of the represented Jet A base, has no
  margin. So the optimiser and the judge score smoke on **different branches**: the optimiser on the primary limit, the judge on the
  alternative. Both end in `uncertified` for smoke, so the final judgement for smoke itself does not differ. But the branch the optimiser
  uses forces aromatics below 8 vol %, which turns a hard spec limit into a `fail`.
* The penalty (lambda = 0.25) is not the cause. It moves the recipe but not the -0.00082 floor.

Fix options. Each one is a declared engine change and needs the usual "feature off gives unchanged v4/v5 results" test:
* (a) In the optimiser, treat by-construction spec minimums (aromatics 8 vol %) as **hard** constraints instead of max-min members.
* (b) When the alternative branch is the only one that can pass, let the optimiser use its point slack as a *graded stand-in*. The judge stays
  strict and still reports `uncertified`.

Either option should turn the P2/P3 `fail` rows into `uncertified`. The designs would then meet every limit at the point estimate. That is
better designs, **not** certification.

## 5. Ranked path to certification

### 5.1 Pure-compound pool with D86 on (closest to a model-level certificate)

The freezing margin is 16.98 C (measured on binaries). Predicted freezing must therefore be at or below -56.98 C (Jet A) or -63.98 C (Jet A-1).
That caps how much heavy material a recipe can hold.

Freezing certifiability for a pool member is decided by `data/raw/sle_constants/tm_dhfus_verified.csv` (`predict_route._tmap_freezing`).
It was checked directly with `library_route.build_route_models`; a member missing from that csv is recorded `coutinho_table` and makes freezing
uncertified. The caps below are ideal SvL with the governing values (`svl_dhfus_kJ_mol`):

| heavy candidate | Tb (C) | can it be a pool member? | freezing constants | max mole fraction (Jet A / Jet A-1) |
|---|---|---|---|---|
| n-dodecane | 216 | yes | verified | 0.025 / 0.013 |
| n-tridecane | 235 | yes | verified (SvL dHfus 36.16 incl. solid-solid) | 0.021 / 0.011 |
| n-tetradecane | 254 | yes | verified | about 0.004 / 0.002 |
| tetralin | 208 | yes | **verified** (12.45 kJ/mol) | 0.54 / 0.43 |
| hexylbenzene | 226 | yes | **not** in the verified csv (Coutinho; CLM-65 did not upgrade it) | high if verified (Tm -61 C) |
| bicyclohexyl | 239 | **no**: no flash-registry data | verified (6.86) | -- |
| 1-methylnaphthalene | 245 | **no**: no flash-registry data | verified (6.945) | -- |

What this means:
* With the constants that govern today, the only heavy components that can go in a pool are n-C12 and n-C13 (2 mole % or less) and tetralin
  (Tb 208 C). That is why P0 cannot reach T90-T10 >= 58 C.
* A pool "P0x" = pool C + tetralin + n-tridecane **can be declared and run now** (no verification needed). Expect it to fall short too:
  tetralin is not heavy enough to lift T90 to about T10 + 58 C, and the flash floor (38 + 2.21 C) pins T10.
* **Action for you that would give the route a real chance:** verify hexylbenzene's Tm/dHfus from a primary source (CLM-65 procedure).
  Then an agent can declare "P0x + hexylbenzene". Getting a flash-registry entry (Antoine + LFL) for bicyclohexyl would add a 239 C cycloalkane.
  Neither is guaranteed to pass.
