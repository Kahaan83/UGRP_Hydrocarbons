# v4 P1 — Provenance audit of the v2/v3 real-fuel tables

Generated by `scripts/v4/audit_provenance.py` (classifier: `src/fuelblend/data/provenance.py`). Ledger: `results/v4/P1/provenance_ledger.csv` (13546 rows, sorted by `table, fuel_id, field`; deterministic).

## What was audited

Every row of: `data/real_fuels/inventory.csv`, `data/real_fuels/compositions.csv`, `data/real_fuels/inventory_measured.csv`, `data/real_fuels/compositions_measured.csv`, `data/real_fuels/inventory_reconstructed.csv`, `data/real_fuels/compositions_reconstructed.csv`, `data/real_fuels/v3/inventory_v3.csv`, `data/real_fuels/v3/compositions_v3.csv`.

Ledger rows per table: one per numeric inventory value (`ron, mon, dvpe_kpa, density_kg_m3, viscosity_kin_cSt, flash_point_C, freezing_point_C, cloud_point_C, pour_point_C, dcn, heat_of_combustion_MJ_kg, number_of_resolved_components, unresolved_fraction, ethanol_vol_pct, ethanol_mass_pct, oxygenate_pct`; NaN cells are *no value* and are skipped), one `claim:<prop>` row per property listed in `available_properties` (the v2 inventories carry no property values, only these claims), and one `fraction:<inchikey>#<n>` row per composition row (`n` = ordinal among rows of the same system with the same InChIKey). The script asserts every inventory fuel and every composition row is covered.

## Method (labels are never trusted)

* **Static (AST):** both ingest scripts (`scripts/v2/ingest_real_fuels_v2.py`, `scripts/v3/ingest_phase1_expansion.py`) are parsed and the code that appends each row dict is *replayed* in a whitelisted evaluator (literal fuel tables, arithmetic, `min/max/round`; no I/O). For each value the ledger records the expression (`script:Lnnn`), whether it is a literal shared by many fuels, a per-fuel literal tuple entry, or arithmetic, and which per-fuel inputs it depends on. Per-fuel loop variables named `cloud`, `dcn`, `dens`, `dens_val`, `dvpe`, `dvpe_val`, `flash`, `freeze`, `mon`, `mon_val`, `pour`, `ron`, `ron_val`, `visc`, `visc40` are treated as *property* inputs.
* **Data:** exact relations are tested on the stored values (`freeze == cloud-3`, `pour == freeze-4`, `flash == round(52+(rho-800)*0.25,1)`, E-blend `dvpe == base + 7.0/3.0`, E-blend volume-weighted density, the FACE gasoline/diesel allocation replayed from RON/MON/density/DCN with the scripts' clip + normalise + round, identical fraction vectors across systems, constants shared by fuels built by the same dict literal, claimed vs actual component counts).
* **Raw files:** `raw_file` requires a per-fuel, per-property match in `extras/fuelblend_data/data/raw`, `data/raw`: CRC 647 (`pour_point/crc647_fuel_properties.csv`, fuel_code = numeric suffix), PRF+ethanol (`octane/face_gasoline_set_I.csv`), FACE+ethanol (`octane/face_gasoline_set_II.csv`), TIGAS / Co-Optima 4-comp / NREL BOB-01 (`cooptima/fuel_engine_co_optimization.csv`), NIST RP-1 molecule list (`rp1/rp1_blends_composition.csv`), surrogate recipes (`surrogates/fuel_surrogates.csv`, SMILES identity + common renormalisation factor + basis), POSF GC classes (`gc_composition/fuel_gc_compositions.csv`). There is no global "value appears somewhere" search.

## Class definitions as applied

* `raw_file` — matches the raw value for this fuel and property (or the raw molecule list with the same SMILES and basis, up to one common renormalisation factor). A `claim:` row (value `listed`) is `raw_file` **only** when the same table stores a value for that property and that stored value is itself `raw_file`; when a raw value exists but the table stores nothing (v2 inventories) or stores a placeholder/formula value, the claim is `unknown` and its evidence reads `raw exists: <path> -> <value>`. Claims carry no data; a keep-filter should use the value rows.
* Two independent detection routes: the code replay, and pure data rules that need no code (the FACE gasoline/diesel allocation replayed from the stored RON/MON/density/DCN, E-blend fractions proportional to a target-derived base, `freeze == cloud-3`, `pour == freeze-4`, the diesel flash formula, E-blend DVPE/density, and one property value on >= 3 fuels of a family -> `placeholder_constant`). `classify_fuel_rows(inv, comp, {})` still flags the FACE compositions, the 43.5 HoC and the CRC 647 constants (tested).
* Property inputs of the replay are found three ways: the variable is written to exactly one property column of a row dict in its loop, its name (list above), or a subscripted read of a property key (`face_map[b]["dens"]`).
* `cited_typed` — narrow: a per-fuel literal typed in the script (or copied from a `data/processed` table that carries a per-row literature reference) with **no** formula, no sharing with other fuels and no conflict with a mapped raw file. Not verified.
* `formula_derived` — reproduced by a formula / replayed expression, including vol→mass conversions with assumed densities, counts derived from the composition table, and model reconstructions.
* `target_derived_composition` — a fraction that depends (through the replayed code) on the same fuel's RON/MON/density/DCN/...; a composition vector is one object, so all rows of such a system (including its lump/normaliser) carry the class.
* `placeholder_constant` — one literal assigned to >=2 fuels by the same dict literal (or one fraction vector shared by >=2 systems), even where it coincides with a raw value.
* `unknown` — not shown to be any of the above; includes typed values that **conflict** with the raw file the script names as its source, mole fractions stored as `basis=mass`, and structural zeros (`0.0` ethanol / unresolved fraction literals).

### CRC 647 reconstructed compositions

They are mapped to **`formula_derived`** with evidence starting `reconstructed:` (`scripts/v2/ingest_real_fuels_v2.py` builds them with `bulk_items`/`to_vector` from fuels.csv bulk aromatics/olefins/diaromatics vol% and D86 points, with a fixed saturate split 0.45/0.35/0.20). They are not measured molecule lists, but they are not computed from the fuels' target properties either (note: D86 is also listed as an available property, so a D86 model on them is partly circular). **Consequence for Task 3:** a rule that keeps only `raw_file`/`cited_typed` would quarantine them; if they should stay usable with a `reconstructed` label, Task 3 must whitelist `formula_derived` rows whose evidence starts with `reconstructed:`. Left for the controller to decide.

## Additional findings (not in the plan)

1. **FACE / PRF ethanol-blend RON/MON vs raw.** 47 v3 RON/MON values conflict with the raw octane file the v3 `source` column names (e.g. FACE A+10 is 92/88 in `face_gasoline_set_II.csv` but 91.7/86.3 in v3; FACE I+10 RON is 79.9 raw vs 100.8 v3). PRF+ethanol RON/MON do match `face_gasoline_set_I.csv` (`raw_file`). Conflicting values are `unknown`.
2. **CRC 647 values in v3 are constants.** 338 CRC 647 property values in inventory_v3.csv conflict with the raw PDF table (density 798.0, viscosity 1.55, flash 45.0, freezing -48.0, pour -52.0, HoC 43.2 for all 57 fuels); 4 of these constants happen to equal the raw value for that fuel (CRC647_20.flash_point_C, CRC647_31.flash_point_C, CRC647_335.freezing_point_C, CRC647_8.flash_point_C) and are still placeholders.
3. **POSF-10325/13511/13516 GC compositions** are hydrocarbon-class percentages (including sub-totals and `*_total` rows, e.g. POSF-10325 sums to 152.28 %) rescaled and mapped to representative molecules by a substring rule (every `*paraffin*` class, including cycloparaffins, becomes n-dodecane) — `formula_derived`, not a measured molecule list.
4. **Surrogate basis mislabel.** 81 composition rows store raw *mole* fractions from `fuel_surrogates.csv` with `basis=mass` (Dooley, HyChem, Kim/Violi, Violi JP-8) — `unknown`. Seven HyChem rows have no SMILES in the raw file and are stored under the key `SURR_nan`.
5. **Component counts.** 48 fuels claim far more resolved components than their composition rows (FACE gasolines claim 78/79 with 4-5 rows; FACE diesels 55 with 4; POSF additional 24 with 3; NASA 8 with 8 n-alkanes only).
6. **Shared recipes.** In v3, 10 systems share an identical fraction vector with another system (POSF additional x5, NASA LFP3/LFP5, Co-Optima 4-comp = TIGAS = NREL BOB-01).
7. **InChIKey does not match SMILES** in 288 composition rows (RDKit check; 19 distinct wrong keys). Examples: the NASA n-alkane rows (v2 and v3) carry the isooctane key on n-C13, the n-heptane key on n-C16 and the n-hexadecane key on n-C10; v3 toluene uses `UAEPNZWRGJTJPN` (v2 uses the correct `YXFVVABEGXRONW`). Any join on InChIKey (e.g. to `data/unified/compounds.csv`) picks up the wrong molecule for these rows.
8. **TRF-60..90** contain only isooctane + n-heptane (no toluene) and set RON = MON = isooctane vol%.

## Limitations

* `cited_typed` values are typed literals that were **not** verified; only the raw files listed above are mapped. FACE base gasoline RON/MON/density/DVPE, FACE diesel DCN/density/viscosity/cloud/pour, POSF additional properties and the diesel surrogate properties have no raw file in the repo.
* A property bound under a new name that is never written to a property column nor read by a property key would not taint the replay; the pure data rules still catch the FACE/diesel cases on the v3 tables, but not on the v2 tables, which store no property values.
* The v2 inventories hold no property values; for them only `claim:` rows and metadata are audited.
* The replay covers the dict literals in the two ingest scripts' `main()`; rows produced elsewhere would show as `unknown`.
